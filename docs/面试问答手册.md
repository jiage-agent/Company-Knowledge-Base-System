# 面试问答手册

> 用法：面试前 30 分钟过一遍"必须记住的 5 个数字"和"三个必讲的坑"。
> 每个问题都按「面试官真正想听什么」来组织，答案控制在 60~90 秒能讲完。

---

## 一、必须记住的 5 个数字

| 数字 | 含义 |
|---|---|
| **19 条 / 7 类场景** | 自建评测集规模，覆盖事实/编号/同义/对比/多跳/拒答/权限 |
| **Recall@5: 0.8816 → 0.9079** | 完整链路相对仅向量检索的提升（+2.6pt） |
| **HitRate@5: 0.8947 → 0.9474** | 用户感知最直接的指标（+5.3pt） |
| **拒答 1/3 → 2/3** | 3 道超纲题里"命中 0 条"的题数（工程保证地知道"我不知道"） |
| **250ms → 1115ms** | 代价：重排让延迟涨了 865ms |

## 二、三个必讲的坑（能主动讲出踩坑过程 = 你真的做过）

1. **统一相关性阈值把指标打崩**
   用一个 `0.02` 的阈值过滤所有阶段，结果"向量+BM25+RRF"档 Recall 从 0.83 掉到 0.158。
   原因：RRF 分数是 `1/(k+rank)` 累加，天然只有 0.01~0.03，0.02 等于全过滤。
   → 结论：跨阶段分数不可比，必须分阶段标定阈值。现在三段各用各的。

2. **HyDE 在企业知识库场景是有害的**
   最初按论文思路让模型"编一段假想答案"再检索，实测它编出了"住宿标准 500 元""董事长审批"这类原文根本没有的内容，把检索彻底带偏。
   → 结论：主动放弃 HyDE，改写只允许使用问题中已有的词。**宁可召回少，也不让幻觉污染检索。**

3. **标题识别把正文吃掉了**
   中文标题正则太宽，把"第一条 员工入职满一年后享受带薪年休假。"整句判成标题，而标题块不参与向量化 → 关键条款全部丢失。
   → 结论：只把「第X章 / 第X节 / 一、/ Markdown #」当结构标题，"第X条"是正文。**静默丢数据比报错更可怕。**

## 三、项目整体

### Q1：这个项目解决什么问题？

企业文档问答有两个真痛点：**检索召回不准** 和 **答案无法追溯**。
再加上企业场景绕不开的第三个：**不同权限的人不能看到彼此的数据**。

我的做法：
- 检索不准 → 混合检索（向量 + BM25 + RRF）+ Cross-Encoder 重排；
- 无法追溯 → 答案带结构化引用锚点（chunk_uid + 文档 + 页码），可点击定位原文；
- 权限隔离 → 租户 / 部门 / 密级 / 角色白名单四元组，**权限条件下推到向量库**；
- 外加一条底线：查不到就说查不到，不许编造（Critic 三重校验 + 相关性阈值）。

### Q2：为什么叫 Agentic RAG？和普通 RAG 有什么区别？

普通 RAG 是固定流水线：检索 → 拼上下文 → 生成，**无论问题难易流程都一样**。
它有三个问题：闲聊也要检索（浪费）、一次检索不准就硬答（幻觉）、处理不了多跳问题。

Agentic RAG 把这些决策显式建模成 LangGraph 的「节点 + 条件边」：
1. **查询理解**：意图分类（事实/对比/多跳/闲聊）+ 决定是否需要检索；
2. **检索规划**：单跳 / 多查询 / 查询分解，重试时强制换策略；
3. **Critic 自检**：证据不足就改写查询重检索（最多 2 轮），仍不足则拒答。

**代价要说清楚**：多几次 LLM 调用，端到端延迟从 ~1s 涨到 3~5s。
所以我保留了 `use_agent=false` 的朴素链路做对照，能现场跑 A/B 对比 —— 不是"为了用框架而用框架"。

## 四、检索链路

### Q3：为什么要混合检索？BM25 和向量各自的价值是什么？

两者互补，不是叠加：
- **向量检索**擅长语义近似（"年假"能匹配"带薪休假"），但对**编号和专有名词**不敏感（`INC-2024-0912`、`P0`、`P99` 这类 token 在训练语料里罕见，向量表示被稀释）；
- **BM25**只看词频与逆文档频率，对精确词匹配极灵敏，但没有语义泛化能力。

我的评测集里专门设计了两类题验证：精确编号类（"工单编号 INC-2024-0912 的格式规范"）和同义改写类（"员工请假出去玩的假期额度"），两类都能答对。

### Q4：为什么用 RRF 而不是加权求和？

**量纲问题**：稠密检索分数是余弦相似度（0~1 连续值），BM25 分数是无上界的对数概率（可能 12.7 也可能 3.2）。直接加权求和会被某一方的数值尺度主导。

RRF 只用**排名**不用分数：`score(d) = Σ wᵢ / (k + rankᵢ(d))`，k 取 60。
好处：免疫量纲差异、对单路异常高分鲁棒、几乎不用调参。
代价：丢掉了"分数差距"的信息。

我实测过权重的影响：`[0.5,0.5]` 时 `c3` 第一，`[0.7,0.3]` 时 `c1` 第一 —— 权重确实能改变结果，所以它是一个有效的调节旋钮（也是消融实验的一项）。

### Q5：重排（Cross-Encoder）和向量检索的本质区别？

- **双塔（Bi-Encoder）**：query 和 doc 分别编码成向量，只算一次内积。快，可以预建索引；但两者从未"见面"，细粒度词级交互信息全丢失，精度有天花板。
- **交叉（Cross-Encoder）**：把 `(query, doc)` 拼在一起送进模型，注意力可逐词交互，精度显著更高；但必须逐对计算，无法预建索引。

所以是漏斗结构：**双塔粗排（万级 → 30 条）+ 交叉精排（30 条 → 5 条）**。

**成本账我算过**：只对融合后的 Top-30 重排，用 `gte-rerank-v2`（不是 large 模型），实测 +865ms。
面试官如果问"这玩意儿不是很慢吗"，我答：慢，但只慢在 30 条候选上，且换来 HitRate +5.3pt。

### Q6：父子块解决了什么矛盾？

**召回精度与上下文完整性的矛盾**：
- 块切小（240 字）：向量表示聚焦、召回准，但喂给大模型时上下文缺失；
- 块切大（900 字）：上下文完整，但一个向量混了多个主题、召回变糊。

解法：子块（240 字）**负责召回**，命中后回填它的父块（900 字）**负责生成**。
代价是多存一份文本（可忽略）。

细节：子块切分我做了「句边界对齐」——最初是直接取上一块末尾 N 个字符做重叠，切出了"需报部门总监审批员工申请年假"这种缝合文本，语义错乱还污染向量。现在重叠取的是**完整的最后一句**。

### Q7：MMR 是干什么的？

Maximal Marginal Relevance，在"相关"和"多样"之间取平衡：
`argmax [λ·sim(q,d) − (1−λ)·max sim(d, d_selected)]`，λ=0.7。

为什么需要：重排后的 Top-5 很可能全是同一段的相邻块（父子块 + 重叠切分时尤其明显），塞 5 个几乎一样的块进 prompt 等于浪费上下文窗口，还会让模型误以为"多处都这么说"，放大幻觉。

## 五、权限与安全（最能加分的一块）

### Q8：权限是怎么设计的？为什么不能只在应用层过滤？

**四元组**：`tenant_id`（租户硬隔离）+ `department`（部门）+ `security_level`（1~4 密级）+ `allowed_roles`（角色白名单）。

**为什么必须下推到向量库**（这是核心答案）：
向量检索是"先算相似度、后返回 Top-K"。如果先取回 Top-K 再在应用层过滤，会有两个问题：
1. **越权风险**：过滤前的候选里已经含有机密内容，任何一处日志或异常打印了候选就等于泄漏；
2. **召回塌缩**：Top-10 里 8 条被过滤掉，只剩 2 条给大模型，答案质量骤降。

所以 `tenant_id / security_level / department` 这些字段**冗余在每个 chunk 上**（向量库不支持 JOIN），过滤条件下推到 Chroma 的 `where` / SQL 的 `WHERE`。

**再加一层应用层兜底校验**（defense in depth）：即使库的过滤语法写错，兜底也能拦住越权 —— 不信任单点。

**实测证据**（可以现场演示）：
```
张三（研发/密级2）问"50万元以上费用谁审批" → 引用里没有财务文档，拒答
李四（财务/密级3）问同一问题          → "由总经理审批 [1]"，引用财务文档
```

### Q9：权限信息放在 JWT 里，用户权限改了怎么办？

这是我做的**有意识的权衡**：把 `tenant_id/role/department/security_level` 写进 JWT，好处是每次请求省一次数据库往返（检索时的权限过滤直接用 token 里的信息）。

代价是：权限变更后需要重新登录才生效，或者走"token 版本号 + Redis 黑名单"来立即失效。
如果业务要求"改密级立即生效"，就得改成每请求查库或用缓存 + 版本号失效。

我选了前者，因为这个系统里权限变更是低频操作，而检索是高频操作 —— 用低频的一致性换高频的性能，是划算的。

### Q10：怎么防止越权？

四道防线：
1. **入库时**带上权限元数据（不是检索时补，那样要回填全部向量）；
2. **检索时**权限条件下推到向量库 + SQL；
3. **返回前**应用层兜底校验（`perm.can_access()`）；
4. **父块回填时**再校验一次（父块与子块密级理论上一致，但代码里不假设这一点）。

另外：跨租户访问统一返回 **404 而不是 403**，避免泄漏"该 id 存在"这一信息。

## 六、生成质量与幻觉控制

### Q11：怎么保证答案不编造？

三层，从便宜到贵：

1. **提示词层**：强制只依据参考资料、给出拒答话术；
2. **规则层（确定性，几乎零成本）**：
   - 引用真实性：答案里的 `[n]` 必须真实存在于本次召回集（**编造引用 = 幻觉的直接证据**）；
   - 数字一致性：答案里的数字必须能在证据原文中找到（正则精确比对）；
3. **模型层**：只在前两条通过后才调用 LLM 判定整体是否被证据支持（省成本）。

**为什么数字要单独校验**（面试官会问"为什么不是校验所有词"）：
知识库问答里最致命的错误是"数字错了"（年假 5 天说成 15 天、报销 450 说成 540），用户很难察觉但后果最严重。而数字是确定性字符，正则能精确校验，成本几乎为零。校验普通措辞既做不准也没必要（语义等价无法用字符串比对）。

### Q12：Critic 判定不通过怎么办？会不会死循环？

不会，有三重保护：
1. **轮次上限**：`MAX_RETRY=2`，超过就拒答；
2. **强制换策略**：重试时一定改写查询（向量检索是确定性的，同样的查询必然返回同样结果，原查询重跑等于纯浪费延迟）；
3. **LangGraph 递归上限**：`recursion_limit=25`，图层面兜底，避免条件循环失控。

**为什么是 2 轮不是 5 轮**：第二轮之后边际收益低于延迟成本。实测一次完整重试链路要 8~12 秒，再多用户就等不下去了。

### Q13：闲聊问题会不会被通用大模型自由发挥？

**这是企业场景的红线，我专门做了处理**：
意图分类判定为闲聊/超纲时，走**受限兜底话术**，只回"我是企业知识库助手，只能回答公司内部文档相关问题"，**不调用通用大模型自由生成**。

原因：员工问"公司明年战略是什么"，模型若自由发挥就是合规事故。
代价是这类问题体验一般，但安全优先 —— 这是设计选择，不是缺陷。

## 七、工程化

### Q14：为什么要做向量库/模型抽象层？

因为要"先用轻量的验证、后续升级"，如果检索代码里到处是 `chroma_collection.query(...)`，换 Milvus 要改遍入库、检索、删除、统计所有地方，风险极高。

把差异收敛到一个接口（`BaseVectorStore`）之后：
- 换库 = 新增一个实现类 + 改 `.env` 一行；
- 上层（混合检索、Agent、评测）完全不用动；
- 还能同时保留两套实现做性能对比。

**接口设计的一个细节**：`search()` 直接接收 `PermissionContext` 作为参数 —— 把"权限下推"变成接口契约的一部分，这样任何人写新实现都不可能忘记带权限条件。**把安全做成默认，而不是靠自觉。**

### Q15：从 ChromaDB 升级到 Milvus，具体升级什么？

三条硬理由（不是跟风）：
1. **过滤能力**：Milvus 支持标量表达式过滤和数组字段 `array_contains`，权限条件可完整下推，不用像 Chroma 那样把角色交集判断挪到应用层；
2. **原生稀疏向量**：Milvus 2.4+ 支持稀疏向量，可以把稠密 + 稀疏放进同一个 collection，省掉现在"向量库 + 自建 BM25 索引"的**双索引一致性问题**（删文档要同步删两处）；
3. **规模与并发**：分布式、多副本、partition key 按 tenant 隔离，扛得住多租户与大数据量。

迁移成本：新增约 200 行适配器，上层零改动（接口已抽象，见 `app/vectorstore/milvus_store.py`）。

### Q16：为什么开发用 SQLite？怎么升级 PostgreSQL？

SQLite 零运维、单文件、pip 装完就能用，适合开发验证。
**升级触发条件不是"用户变多了"，而是**：需要多 worker 部署（SQLite 写并发/跨进程共享是瓶颈）、或者数据量上到需要连接池与并发写。

因为用了 SQLModel/SQLAlchemy 2.0 异步引擎，升级**只改 `.env` 里的 `DATABASE_URL`**（`sqlite+aiosqlite://` → `postgresql+asyncpg://`），业务代码一行不用改。这是"先用轻量方案验证"能成立的前提 —— 一开始就别把 SQL 写死在业务逻辑里。

### Q17：入库流程怎么保证不出半截数据？

**状态机 + 分段记录**：`PENDING → PARSING → INDEXING → INDEXED / FAILED`，每阶段耗时与错误单独落库，失败时 `error_message` 精确到哪个阶段。

**写入顺序**：先写关系库（事实来源）→ 再写向量库。
如果反过来（先写向量库成功、写库失败），会出现"检索得到但查不到元数据/权限"的幽灵数据；而我们的顺序最坏只是"暂时检索不到"，可以重跑补偿 —— **宁可少，不可脏。**

**幂等**：上传先算文件的 SHA256，同租户下相同内容直接返回已有文档，不重复解析、不重复向量化（既省成本，也避免向量库出现重复数据）。

### Q18：chunk_uid 为什么要确定性生成？

`d{doc_id}v{version}c{序号}`，不用随机 uuid，三个理由：
1. **幂等**：重复入库不产生重复向量；
2. **可复现**：评测集标注的 gold chunk_uid 在重建索引后依然有效（随机 uid 会导致每次重建评测基线失效，无法对比）；
3. **可定位**：能按前缀精确找到某份文档的所有向量。

**代价**：与"软删除保留历史块"冲突（UNIQUE 约束不允许同 uid 两行），所以重建索引时要物理删除旧块。
真实生产如果合规要求保留历史快照，就该改成 uid 带版本号，并给评测集做 uid 映射表 —— **关键不是选哪个，而是知道各自的代价。**

## 八、评测与效果（最能体现工程素养）

### Q19：你怎么知道效果好？指标是什么？

自建 **19 条评测集**，覆盖 7 类场景：事实查询、精确编号、同义改写、对比、多跳、拒答、权限。

**检索指标**（不需要 LLM，零成本可反复跑）：
- `Recall@K`：Top-K 是否包含正确块；
- `MRR`：正确块排第几位；
- `NDCG@K`：排序质量的加权版本；
- `HitRate@K`：至少命中一个的比例。

**为什么要一起看**：Recall 高但 MRR 低说明"找得到但排得靠后"，大模型很可能因为排序靠后而忽略它。

**消融实验结果**：

| 配置 | Recall@5 | NDCG@5 | HitRate@5 | 延迟 |
|---|---|---|---|---|
| 仅向量 | 0.8816 | 0.8314 | 0.8947 | 250ms |
| +BM25+RRF | 0.8289 | 0.8057 | 0.8421 | 280ms |
| **+重排（完整）** | **0.9079** | **0.8588** | **0.9474** | 1115ms |

### Q20：如果指标不好看你会怎么调？（这题是陷阱，考的是方法论）

按"性价比"顺序排查：
1. **先看标注**：gold 是用关键词反查的，关键词太常见会导致 gold 集合虚高（比如"10天"命中了多个块），先修评测集再调系统 —— **指标不可信时，调优就是瞎调**；
2. **看切分**：块太大 → 语义稀释；块太小 → 上下文断裂。这是收益最大的一环；
3. **看召回**：调 `DENSE_TOP_K / SPARSE_TOP_K / RRF 权重`，做小规模网格搜索；
4. **看重排**：换模型、调 `RERANK_TOP_N`；
5. **最后才动提示词**：提示词的影响通常小于检索质量，"检索错了，提示词再漂亮也救不回来"。

**我也踩过反面教训**：曾经用一个统一的 0.02 相关性阈值，把"向量+BM25+RRF"档从 0.83 打到 0.158。原因就是 RRF 分数天然只有 0.01~0.03，统一阈值等于全过滤 —— 所以现在三段各自标定阈值。

### Q21：评测集是怎么造的？为什么可信？

两种来源：内置种子评测集（开箱即用）+ 外部 JSON（便于扩充）。

每条样本标注 `gold_keywords` 而不是直接标 chunk_uid，评测时用关键词**反查当前索引**得到 gold 集合。
好处：重建索引、改切分策略后评测集依然复用，不需要重新标注。

**我也要诚实说明局限**：19 条样本统计置信度有限，应该扩到 150~300 条并人工校验；关键词反查会引入噪声（`gold_count` 从 0 到 4 都有，说明标注粒度不一致）。这是下一步要做的事。

## 九、可能的"压力测试"问题

**Q：你这个跟市面上的开源项目有什么区别？**
三个点：① 权限感知检索（四元组 + 条件下推 + 双重防护），不是"加个 tenant_id 字段"；② 有量化评测与消融实验，指标可复现；③ 所有模型/存储都可热切换（改配置不改代码），有明确的升级路径与触发条件。

**Q：为什么不用现成的 LangChain RAG 链？**
`RetrievalQA` 这类封装把流程写死了，而我需要条件路由、重试回环、引用校验这些自定义节点。LangGraph 的 StateGraph 让流程变成显式的"状态 + 节点 + 边"，可单测、可观测、可解释。另外自己实现 BM25、RRF、MMR 这些组件，也是为了让每一环都可控可调。

**Q：这个项目有多少代码是你自己写的？**
核心链路（解析、切分、混合检索、RRF、MMR、Critic 校验、权限模型、评测）都是自己实现并实测调过的；框架用的是 LangGraph / FastAPI / ChromaDB 这些成熟库。踩过的坑（阈值量纲、HyDE 幻觉、标题误判、greenlet 会话状态）都记录在代码注释和 README 里。

**Q：如果让你重做，你会怎么改？**
① 一开始就把入库做成异步任务队列（同步入库在大文件上会超时）；② 评测集先扩到 200 条再动手调优（先有尺子再改东西）；③ 语义缓存从第一天就加（企业知识库重复提问率很高，缓存是成本与延迟的第一杠杆）；④ 分数归一化做在检索层而不是每个阶段各自标阈值。
